# HANDOFF: observability-query-builder backend

Read this before doing anything else with this folder. It's written for two
audiences at once: **you**, testing this before handing it off, and **the
frontend team**, integrating against it. Where something only matters to one
of you, it says so.

---

## 1. What this service does, in one paragraph

The frontend sends a natural-language question to `POST /api/v1/query`. The
backend figures out which metric/measurement the question needs (Router),
builds the actual PromQL or OpenSearch DSL query (Generator), mechanically
checks that query for correctness before trusting it (Validator — no AI
involved in this step, see §5), runs it against Prometheus and/or OpenSearch
(Executor), and hands back frontend-ready JSON: labeled data series for line
charts, buckets for bar charts/tables, or raw log hits for a log viewer. The
frontend's job starts where this backend's response ends — deciding chart
type, summarizing, rendering. This backend never does that.

One narrow exception to "read-only": if `ALERT_RULE_CREATION_ENABLED` is
set, the same question can also PROPOSE creating a brand-new Grafana alert
rule — never automatically, always behind a separate explicit confirmation
call. See §9. Off by default; skip §9 entirely if you're not using it yet.

## 2. Running it / connecting to it

```bash
cp .env.example .env        # fill in a real GEMINI_API_KEY
python run_server.py
```

| What | Where | Notes |
|---|---|---|
| The API itself | `http://localhost:8000` | `API_HOST`/`API_PORT` in `.env` |
| Prometheus | `http://localhost:9090` | `PROMETHEUS_URL` in `.env` — already running per your setup |
| OpenSearch | `http://localhost:9600` | `OPENSEARCH_URL` in `.env` — already running per your setup |
| Interactive API docs | `http://localhost:8000/docs` | Auto-generated by FastAPI, useful for the frontend team to poke at without writing code first |

CORS is wide open (`CORS_ALLOW_ORIGINS=["*"]`) and there's no API key
required by default — correct for local development, both documented in
`.env.example` with a note on what to change before this is ever deployed
anywhere reachable outside your own machine.

## 3. What the frontend sends

`POST /api/v1/query`, JSON body:

```json
{"question": "compare CPU utilization on node-1 and node-2 over the last hour"}
```

```json
{"question": "the available one, not free", "session_id": "a1b2c3d4-..."}
```

| Field | Required | Notes |
|---|---|---|
| `question` | yes | Free-text. Also used as the answer to a clarifying question — see §6. |
| `session_id` | no | Only present when replying to a clarification (§6). Omit for a fresh question. |

That's the entire input contract for `POST /api/v1/query` — one field, one
endpoint, for every kind of question — single-metric, multi-metric,
comparison, follow-up clarification. `POST /api/v1/alerts/confirm` (§9.2)
is a separate endpoint with its own, deliberately narrower, input contract
(`session_id` + optional `confirm`) — it's not reachable through this one.

---

## 4. What the frontend gets back — the output contract

Every response is:

```json
{"result": { ... }, "session_id": null}
```

`session_id` is non-null **only** when the backend needs a clarifying answer
before it can proceed (§6) — in that case `result` is NOT executed yet (no
data), and the frontend must send the follow-up as a new request carrying
that `session_id`.

`result` always has a `mode` field: `"single"` (one measurement resolved) or
`"multi"` (two or more). This is the one piece of branching logic the
frontend needs:

```js
const entries = result.mode === "multi" ? result.results : [result];
for (const entry of entries) {
  // handle `entry` the same way regardless of which branch it came from —
  // every entry, in both modes, has the exact same set of possible shapes.
}
```

### 4.1 Every shape `entry.status` can be

| `status` | Means | Has `execution`? | Frontend should… |
|---|---|---|---|
| `ok` | Query ran normally. | **Yes** | Render `entry.execution` (§4.2). |
| `panic_mode_best_effort` | Question was underspecified; broadest reasonable interpretation was used. | **Yes** | Same as `ok`, but show `entry.caveat` near the chart — the interpretation was a guess, not a certainty. |
| `ambiguous_metric` | Two+ metrics plausibly match; needs a human pick. | No — never executed | Show `entry.clarification` as a question, `entry.candidates` (`[{name, purpose}]`) as options. Send the user's pick back as a new `question` with the returned `session_id`. |
| `unsupported_metric` | The question wants something this skill package explicitly does not cover (see the matched reference's Do-Not-Use list). | No | Show `entry.explanation`. Nothing to retry — this isn't a "not implemented yet," it's "not applicable." |
| `unmapped` | Nothing in the currently-loaded skill covers this measurement. **This is the status OpenSearch questions get today** — see §7. | No | Show `entry.explanation`. This is expected and will resolve itself once OpenSearch domain coverage ships — no frontend change needed then. |
| `declined` | Nonsensical input, a prompt-injection attempt, or a parameter that needs clarifying (`entry.reason` tells you which). | No | If `reason === "parameter_requires_clarification"`, treat exactly like `ambiguous_metric` (`entry.clarification`, reply with `session_id`). Otherwise just show `entry.explanation`. |
| `out_of_scope_action` | Asked to silence, acknowledge, delete, restart, or otherwise modify something that already exists — this backend never mutates an existing resource, no exception. (Creating a brand-new alert rule is a separate, narrow exception — see the `alert_rule_proposed` row below and §9.) | No | Show `entry.explanation`. Never retryable. |
| `alert_rule_proposed` | **Only when `ALERT_RULE_CREATION_ENABLED=true` (§9).** A brand-new Grafana alert rule was resolved from a verified metric and is ready to create — but hasn't been yet. | No — never executed by `POST /api/v1/query` | Show `entry.alert_rule` (title, condition, threshold, duration) for the user to review, then send `session_id` to `POST /api/v1/alerts/confirm` (§9.2) to actually create it, or to discard it (`"confirm": false`). |
| `validation_failed` | **Not part of the skill's own status vocabulary** — see the callout below. | No | Treat exactly like `declined`: show `entry.explanation`, nothing to retry. |

> **What is `validation_failed`?** Before any query reaches Prometheus/
> OpenSearch, this backend mechanically checks it — is every metric name one
> that's actually documented, is every label key one that was actually
> confirmed to exist right now, does the time range make sense, and so on
> (see §5). If that check ever fails, the frontend gets `validation_failed`
> instead of a made-up chart. **You should never see this in normal use** —
> if you do, it means a bug slipped through, and it's worth telling
> the backend maintainer (it'll also be in the server logs with the exact
> mechanical reason it failed). It behaves identically to `declined` from
> the frontend's point of view: show the explanation, nothing to retry.

`mode: "multi"` responses additionally carry `synthesis`: either `null`, or
a short natural-language string tying the multiple results together (e.g.
"Both nodes are under 40% CPU utilization over the last hour.") — safe to
show as a one-line summary above the individual charts, when non-null.

### 4.2 The `execution` block — the actual data

Only present on `ok` / `panic_mode_best_effort` entries. Always has these
four fields, then result-shape-specific ones:

```json
{
  "execution_status": "success",
  "result_type": "series",
  "endpoint": "http://localhost:9090/api/v1/query_range",
  "fetched_at": "2026-08-17T10:15:00Z"
}
```

`execution_status` — **check this first, always**:

| Value | Means |
|---|---|
| `success` | Data came back, non-empty. |
| `empty_result` | Query ran fine, backend just has no matching data right now (e.g. asking about a node that isn't currently reporting). Not an error — show "no data for this range," not an error state. |
| `endpoint_error` | Prometheus/OpenSearch was unreachable, timed out, or rejected the query. `error` field has the detail. Show a real error state; safe to let the user retry. |
| `not_executed` | Internal routing problem (shouldn't happen in normal use, same spirit as `validation_failed` above). |

Then, keyed off `result_type`:

**`"series"`** — for line/multi-line charts:
```json
{
  "result_type": "series",
  "series": [
    {
      "labels": {"instance": "node-1:9100", "mode": "idle"},
      "legend_label": "instance=node-1:9100, mode=idle",
      "points": [{"timestamp": "2026-08-17T09:15:00Z", "value": 0.42}]
    }
  ],
  "series_count": 1,
  "had_invalid_samples": false,
  "truncated": false
}
```
`legend_label` is pre-built and safe to render directly on a chart legend —
you never need to reconstruct one from `labels` yourself. `points[].value`
can be `null` (a genuinely missing/unstable sample was hit and safely
dropped rather than sent as invalid JSON) — render it as a gap, not a zero.
When there's more than one series (a comparison question), a `comparison`
key is also present, carrying `{metric_name, series_summaries: [{legend_label,
min, max, avg, latest}]}` — enough to build a "which one is higher"
legend/table without re-deriving it from raw points.

**`"buckets"`** — for bar charts / tables (OpenSearch terms aggregations,
not live yet — see §7):
```json
{"result_type": "buckets", "buckets": [{"key": "node-1", "doc_count": 42}], "bucket_count": 1}
```

**`"hits"`** — for a log viewer / table (OpenSearch plain search, not live
yet — see §7):
```json
{"result_type": "hits", "hits": [{"timestamp": "...", "severity": "ERROR", "body": "...", "resource": {}, "attributes": {}}], "hit_count": 1, "total_hits": 137}
```

Every shape also carries `had_invalid_samples` (bool — some raw samples were
dropped as NaN/Inf/malformed; the rest of the data is still trustworthy) and
`truncated` (bool — the result was capped by a safety limit in `.env`;
`original_count` tells you the true size when this is `true`).

### 4.3 A full worked example

```json
{
  "result": {
    "mode": "single",
    "status": "ok",
    "reference_used": "references/node-exporter/cpu.md",
    "measurement_used": {"type": "raw_metric", "name": "node_load1", "source_metrics": []},
    "data_source": "prometheus",
    "query": "node_load1{instance=\"node-1:9100\"}",
    "time_range": {"from": "now-1h", "to": "now", "step": "60s"},
    "explanation": "1-minute load average for node-1 over the last hour.",
    "execution": {
      "execution_status": "success",
      "result_type": "series",
      "endpoint": "http://localhost:9090/api/v1/query_range",
      "fetched_at": "2026-08-17T10:15:00Z",
      "series": [{
        "labels": {"instance": "node-1:9100"},
        "legend_label": "instance=node-1:9100",
        "points": [{"timestamp": "2026-08-17T09:15:00Z", "value": 0.42}]
      }],
      "series_count": 1,
      "had_invalid_samples": false,
      "truncated": false
    }
  },
  "session_id": null
}
```

## 5. "Validation is deterministic" — what that means and why it matters to you

Every query this backend builds is checked by plain Python (`app/validator.py`)
before it's ever run against Prometheus or OpenSearch — no AI model is asked
to grade another AI model's work, and the same input always produces the
same pass/fail result. It mechanically confirms:
- the metric name used actually exists in the documented Metric Directory
  (never a name the AI invented),
- every label key used in the query was actually confirmed to exist against
  the live Prometheus instance moments earlier (never guessed "by analogy"
  — e.g. it'll block a query that assumes a `node_id` label exists if only
  `instance` was ever actually confirmed),
- the time range and step match the documented grammar and resolve to a
  sane start-before-end range,
- the response shape matches SKILL.md's Output Contract exactly,
- (only for `alert_rule_proposed`, §9) the alert condition actually
  references the resolved metric, and a threshold/comparison/duration/
  folder are all present — never fabricated, and never silently left out.

If any of that fails, the frontend gets a clean `validation_failed` result
(§4.1) instead of a chart built on a query that might be wrong. This is also
why the response is a bit slower than "one AI call" — it's two AI calls
(understand the question, build the query) plus this mechanical check, not
three AI calls like an earlier version of this backend used.

**One nuance worth knowing:** the validator distinguishes *envelope*
problems from *content* problems. If the Generator forgets the top-level
`"mode"` wrapper around an otherwise well-formed result, the pipeline
repairs that automatically before validating (`pipeline._normalize_contract_
shape`) — that's pure structure, not a fabricated fact. If instead a
required *content* field is missing or wrong (e.g. the Router misclassifies
a plain "show me X" request as `out_of_scope_action` and can't supply a real
`requested_action`), the validator correctly refuses to paper over it with
an invented value — you'll see `validation_failed`, and that's the system
working as intended, not a bug to silence.

## 6. The clarification flow (multi-turn)

Some questions are genuinely ambiguous ("show me the available metric" —
available memory? available disk?) or missing something the backend can't
guess (which node?). When that happens:

1. `result.session_id` (top-level, not inside `result`) is non-null, and
   `result` itself has `status: "ambiguous_metric"` or `status: "declined"`
   with `reason: "parameter_requires_clarification"`.
2. Show the user `result.clarification` (a question) and, for
   `ambiguous_metric`, `result.candidates` as pickable options.
3. Send their answer as a normal `POST /api/v1/query`, with `question` set
   to their answer and `session_id` set to the value you got back. The
   backend resolves it using the FULL original question plus their answer —
   don't try to combine them into one string yourself.
4. Sessions expire after `SESSION_TTL_SECONDS` (600s / 10 min by default).
   An expired/unknown `session_id` gets HTTP 410 — treat that as "just ask
   again from scratch."

In `mode: "multi"` responses, if even ONE entry needs clarification, the
**entire** response holds off on execution (all entries), not just that one
— answering the clarification can change how the whole multi-part question
gets resolved, not just patch one piece of it.

**This same session mechanism is also reused for `alert_rule_proposed`**
(§9.2) — but answered by a *different* endpoint
(`POST /api/v1/alerts/confirm`, not `POST /api/v1/query`), since confirming
an alert-rule creation is a fundamentally different action than answering a
clarifying question, even though both hold a session the same way.

## 7. Current OpenSearch status — read this before building any OpenSearch-dependent UI

**Short version: Prometheus questions work end-to-end today. OpenSearch
questions currently come back as `unmapped`, with a clear explanation — not
silently failing, not returning fake data.**

Longer version: the *execution* side for OpenSearch (the HTTP client,
live field discovery, response normalization into series/buckets/hits) is
fully built and unit-tested against realistic mocked responses. What's
missing is the *routing* side — no domain reference file yet tells the
skill "here's what OpenSearch data means and how to query it," because
you're still authoring that content. `skills/references/opensearch-
fundamentals.md` exists (query mechanics only) but is explicitly marked
**infrastructure only, no exporter or domain routes here yet** — see its own
status banner, and `SKILL.md`'s routing table row for it.

Concretely, right now:
- A pure-OpenSearch question ("show me recent error logs for node-1") comes
  back `mode: "single", status: "unmapped"`, with an explanation.
- **A compound question needing both** ("show CPU load and recent error
  logs for node-1") does **not** fail as a whole, and does **not** silently
  drop the logs half. The CPU half resolves and executes completely
  normally; the response becomes `mode: "multi"` with one normal `ok` entry
  for the CPU data and one `unmapped` entry explaining the logs half isn't
  covered yet:

  ```json
  {
    "result": {
      "mode": "multi",
      "results": [
        {"status": "ok", "data_source": "prometheus", "execution": {"execution_status": "success"}},
        {"status": "unmapped", "explanation": "No reference in the currently-loaded skill package covers: recent error logs for node-1. needs an OpenSearch-backed log measurement; no domain reference currently defines one."}
      ],
      "synthesis": null
    },
    "session_id": null
  }
  ```

  Build your frontend's multi-result rendering to expect this shape now — a
  mixed list of resolved and unmapped entries — rather than assuming every
  entry in `results` is always renderable data.

**When your OpenSearch skill content ships** (routing rows + domain files),
nothing in this backend's code needs to change. Add the reference files per
`skills/EXTENDING.md`'s "Adding a New Domain File" / "Adding a New
Datasource" sections, add the routing rows to `SKILL.md` §4, hit
`POST /api/v1/admin/reload-skill` (or restart) — OpenSearch questions start
resolving and executing the same way Prometheus questions do today, no code
change, no frontend contract change. This is the mechanism described in §8.

Use `GET /api/v1/capabilities` any time to see, programmatically, exactly
which topics are currently routed vs. which rows exist but are marked
`"pending"` or carry an infrastructure-only `"note"` — useful for greying
out a UI affordance ahead of time instead of learning it from a failed query.

## 8. How "dynamic" this actually is — adding new coverage later

This was a specific design requirement, so it's worth being precise about
what "automatic" actually covers.

**Fully automatic, zero code change, ever:**
- A new **metric** added to an existing domain file (e.g. a new CPU metric
  in `cpu.md`) — picked up the moment the file is re-read (every request;
  reference file content is never cached).
- A new **label key** appearing on an existing metric in Prometheus (e.g.
  someone adds a `datacenter` label to `node_cpu_seconds_total` tomorrow) —
  `label_discovery.py` queries Prometheus's own metadata live, every
  request. Nothing about label keys is ever hardcoded anywhere in `app/`.

**Automatic after a restart, or `POST /api/v1/admin/reload-skill`
(no restart needed):**
- A new **domain file** (e.g. `disk-io.md`) with its own metrics, once it
  has (a) a Metric Directory row in its exporter's `overview.md` and (b) a
  routing-table row in `SKILL.md` §4. `skill_index.py` parses both
  dynamically — nothing in `app/` names a specific exporter, domain, or
  metric anywhere.
- A brand-new **exporter** or **datasource**, same mechanism.

Follow `skills/EXTENDING.md` exactly for the authoring steps (it's
maintainer-facing, thorough, and already covers "Adding a Metric," "Adding
a New Domain File," "Adding a New Exporter," and "Adding a New Datasource"
each as a numbered checklist) — that document, not this one, is the source
of truth for how to author new skill content correctly.

## 9. Alert Rule Creation (SKILL.md §12) — read this before turning it on

**Disabled by default** (`ALERT_RULE_CREATION_ENABLED=false` in
`.env.example`). This is the one narrow, explicit exception to this
backend's read-only nature: with the flag on, a question like "alert me if
CPU exceeds 90%" can PROPOSE creating a brand-new Grafana alert rule. It is
never created automatically — a separate, explicit confirmation call is
always required — and it never extends to silencing, deleting, or modifying
an alert that already exists, flag on or off.

### 9.1 Required Grafana-side setup

You need a running Grafana instance with a Prometheus datasource pointing
at the **same** Prometheus this backend already queries via
`PROMETHEUS_URL` — a proposed rule's condition is plain PromQL evaluated by
Grafana against whatever datasource UID you configure, so a mismatch here
doesn't error, it just silently evaluates against the wrong series. Before
setting `ALERT_RULE_CREATION_ENABLED=true`:

1. Create a Grafana **service account** (Administration → Service
   accounts) with at least the **Alert Rule Writer** role, and generate a
   token from it.
2. Note the **folder UID** you want new rules created into (Alerting →
   Alert rules → your folder; the UID is in the URL, not the folder's
   display name).
3. Note the **datasource UID** of the Prometheus datasource pointing at
   your existing Prometheus (Connections → Data sources → your datasource;
   again, the UID is in the URL).
4. Fill in `.env`'s `GRAFANA_URL`, `GRAFANA_SERVICE_ACCOUNT_TOKEN`,
   `GRAFANA_DEFAULT_FOLDER_UID`, and `GRAFANA_DEFAULT_DATASOURCE_UID` — all
   four are required once the flag is on; `app/grafana_client.py` fails
   closed with a clear error rather than guessing if any is missing.
5. Run `python3 scripts/smoke_test_grafana.py` — confirms the token is
   valid and both UIDs actually exist and are visible to it, before you
   try a real question.
6. Set `ALERT_RULE_CREATION_ENABLED=true`.

### 9.2 The propose → confirm flow

This is a **two-step** flow, deliberately — the same shape as the
clarification flow in §6, reusing the exact same session mechanism, but
answered by a different endpoint because confirming is a fundamentally
different action than answering a clarifying question:

1. Ask a normal question through `POST /api/v1/query`:
   `{"question": "alert me if CPU exceeds 90% on node-1 for 5 minutes"}`.
2. If it resolves cleanly, you get back `result.status ===
   "alert_rule_proposed"` (new row in §4.1's table below) with a non-null
   `session_id` — **nothing has been created in Grafana yet.** Show the
   user `result.alert_rule` (title, condition, threshold, duration) and ask
   them to confirm.
3. Send their confirmation to a **different** endpoint,
   `POST /api/v1/alerts/confirm`, with just the `session_id`:
   `{"session_id": "<the id from step 2>"}`. This is the only call in the
   whole flow that actually writes to Grafana. Set `"confirm": false`
   instead to discard the proposal without creating anything.
4. On success: `{"status": "created", "rule_uid": "...", "deeplink":
   "http://.../alerting/grafana/.../view"}` — safe to link the user
   straight to the rule in Grafana. See README.md's API section for the
   full response shape, including every non-success `status` value.
5. Like a clarification session, this is single-use and TTL-bound
   (`SESSION_TTL_SECONDS`, same 600s default) — an expired/already-used
   `session_id` gets HTTP 410 from either endpoint, same as §6.

**Why a plain question can't create a rule in one call:** every alert
rule's condition and threshold has to trace back to something explicitly
verified (SKILL.md §12.4) and the user has to see and explicitly agree to
exactly what will be created — a threshold, folder, or condition is never
guessed on their behalf. If a required piece (threshold value, comparison
direction) is missing from the question, you get `status: "declined"`,
`reason: "parameter_requires_clarification"` instead — handle it exactly
like any other clarification (§6), it just happens to be gathering
information for an eventual alert proposal rather than a chart.

### 9.3 What you will and won't see

Most metrics today don't have a verified alert condition yet — only
`node_cpu_seconds_total` does, as of this version (see
`skills/references/node-exporter/cpu.md`'s Alert query/threshold field).
Asking to create an alert for anything else currently comes back
`status: "unsupported_metric"`, explaining plainly that no verified alert
query is defined for that metric yet — this is expected, not a bug, and
matches the same "never fabricate" discipline every other part of this
skill package already follows for query construction. As more metrics get
a verified Alert query/threshold field (`skills/EXTENDING.md`'s authoring
conventions cover this field the same way they cover Query Examples),
alert-rule creation becomes available for them automatically — no code
change, same mechanism as §8.

**Silencing, deleting, or modifying an existing alert is never in scope,**
flag on or off — a request like "silence this alert" or "delete that alert
rule" always comes back `status: "out_of_scope_action"`, unchanged from
every prior version of this backend.

## 10. New-version replacement policy

You said the plan is: hand this off, keep improving OpenSearch coverage
separately, and later just replace the `backend/` folder wholesale in the
frontend team's copy of the repo. That's exactly how this was built to work:

- **Safe to just swap the whole folder, any time.** The API contract (§3,
  §4) is the stable boundary — a future version can rewrite anything inside
  `app/` or add new domain files under `skills/` without the frontend
  noticing, as long as `POST /api/v1/query`'s request/response shape here
  doesn't change.
- **What WOULD be a breaking change** (none of these have happened in this
  handoff, but flagging so you recognize one if a future version does it):
  a new required top-level field frontend code doesn't handle, a renamed
  `status` value, a renamed `execution_status` value, or a changed meaning
  for an existing field. If a future version ever needs one, it should
  be called out explicitly in that version's own handoff notes, the same
  way this document exists now.
- **Config drift is the actual risk, not code.** Before swapping, diff the
  new `.env.example` against your running `.env` — a future version might
  add a new setting with a sensible default (harmless to miss) or, rarely,
  rename one (would need updating). Everything in `.env.example` has an
  inline comment explaining what it does.
- **This version's specific contract additions**, for the record: the
  `unresolved_topics` → `unmapped`-entries mechanism in §7/§8, the
  `validation_failed` status in §4.1, and (this version) the
  `alert_rule_proposed` status plus the new `POST /api/v1/alerts/confirm`
  endpoint (§9) — disabled by default via `ALERT_RULE_CREATION_ENABLED`,
  so it changes nothing for a deployment that doesn't opt in. All are
  additive — nothing already built against `ok`/`ambiguous_metric`/etc.
  needs to change.

## 11. Testing this before you hand it off

### 11.1 Automated tests (run these first, always)

```bash
pip install -r requirements-dev.txt
pytest -q
```

Every single test mocks the LLM and the backends — this checks the
backend's own logic (routing decisions, query construction rules, the
deterministic validator, response normalization, error handling, the whole
API layer) with zero dependency on a live Gemini key or a running
Prometheus/OpenSearch. **All of them should pass, always, on a fresh
checkout with no `.env` file at all.** If one fails, that's a real
regression — this suite is the safety net for every future change,
including the frontend team's.

This is NOT a substitute for live testing (below) — it cannot verify that
the Gemini API call actually works, or that the prompts actually produce
good PromQL against a real question. It verifies the backend's own code is
correct; it can't verify the AI model's behavior, because the AI model
itself is mocked out on purpose (that's what makes it possible to run this
suite in a few seconds with no API key at all).

### 11.2 Live testing (do this before trusting real answers)

**Neither I nor the previous version of this backend could reach Google's
Gemini API or your local Prometheus/OpenSearch from the sandbox environment
this was built in — no network path to either.** This is stated plainly so
you know exactly what has and hasn't been verified: everything in §11.1 has
been run and passes; nothing that requires a live Gemini/Prometheus/
OpenSearch connection has been. Run these, in order, on your own machine:

1. **`python3 scripts/smoke_test_prometheus.py`** — confirms your local
   Prometheus is reachable the way the code expects (right URL, right API
   shape). Fastest thing to check first since it needs no API key.
2. **`python3 scripts/smoke_test_gemini.py`** — confirms the Gemini SDK call
   itself works with your real `GEMINI_API_KEY`. If this fails with a 404
   naming a specific model, that model's been retired — check
   `https://ai.google.dev/gemini-api/docs/models` and update `GEMINI_MODEL`
   in `.env`.
3. **Start the server** (`python run_server.py`)
   and work through `skills/evals/regression-cases.md` — hand-authored
   questions specifically designed to cover routing correctness, ambiguity
   handling, comparisons, panic mode, and label-fabrication prevention. For
   each one, send it to `POST /api/v1/query` and confirm the `status` and
   general shape match what the case describes. This is the real
   correctness check — it's testing the AI model's actual behavior against
   real prompts, which nothing automated here can do for you.

   > [!NOTE]
   > **Windows PowerShell note:** In PowerShell, `curl` is an alias for `Invoke-WebRequest` which has different parameter semantics. Use **`Invoke-RestMethod`** or call **`curl.exe`** directly:
   >
   > **PowerShell (Invoke-RestMethod):**
   > ```powershell
   > Invoke-RestMethod -Uri http://localhost:8000/api/v1/query -Method Post -ContentType "application/json" -Body '{"question": "What is the CPU utilization on node-3?"}'
   > ```
   > **PowerShell (curl.exe):**
   > ```powershell
   > curl.exe -s -X POST http://localhost:8000/api/v1/query -H "Content-Type: application/json" -d "{\"question\": \"What is the CPU utilization on node-3?\"}"
   > ```
   > **Bash / macOS / Linux (curl):**
   > ```bash
   > curl -s -X POST http://localhost:8000/api/v1/query -H 'Content-Type: application/json' -d '{"question": "What is the CPU utilization on node-3?"}'
   > ```

4. **Specifically test the multi-datasource partial-coverage behavior**
   from §7 with a real compound question ("show me CPU load and error logs
   for node-1") — confirm you get the `mode: "multi"` shape with one `ok`
   entry and one `unmapped` entry, not a dropped half or a whole-question
   failure.
5. **Specifically test a clarification round-trip** (§6) — ask something
   genuinely ambiguous, confirm you get `session_id` back, send the
   follow-up, confirm it resolves using the combined context:
   ```powershell
   # PowerShell follow-up query with session_id
   Invoke-RestMethod -Uri http://localhost:8000/api/v1/query -Method Post -ContentType "application/json" -Body '{"question": "CPU utilization", "session_id": "<SESSION_ID>"}'
   ```
6. **If you turned on `ALERT_RULE_CREATION_ENABLED`:** run
   `python3 scripts/smoke_test_grafana.py` first (§9.1), then test the
   full propose → confirm round-trip (§9.2) — ask "alert me if CPU exceeds
   90% on node-1 for 5 minutes", confirm you get `status:
   "alert_rule_proposed"` with a `session_id` and nothing yet created in
   Grafana, then `POST /api/v1/alerts/confirm` with that `session_id` and
   confirm the rule actually appears in Grafana's alert list:
   ```powershell
   # PowerShell alert confirmation call
   Invoke-RestMethod -Uri http://localhost:8000/api/v1/alerts/confirm -Method Post -ContentType "application/json" -Body '{"session_id": "<SESSION_ID>", "confirm": true}'
   ```
   Also test `"confirm": false` and confirm nothing gets created. Also re-confirm
   "silence this alert" still comes back `out_of_scope_action` — this flag
   must never change that.

- [ ] `pytest -q` passes completely, on a clean checkout.

- [ ] At least the routing + ambiguity + comparison cases in
