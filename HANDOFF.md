# HANDOFF: observability-query-builder backend

Read this before doing anything else with this folder. It's written for two
audiences at once: **you**, testing this before handing it off, and **the
frontend team**, integrating against it. Where something only matters to one
of you, it says so.

---

## 1. What this service does, in one paragraph

The frontend sends a natural-language question to `POST /api/v1/query`. The
backend figures out which metric/measurement the question needs (Router),
builds the actual PromQL or OpenSearch DSL query (Generator), mechanically
checks that query for correctness before trusting it (Validator — no AI
involved in this step, see §5), runs it against Prometheus and/or OpenSearch
(Executor), and hands back frontend-ready JSON: labeled data series for line
charts, buckets for bar charts/tables, or raw log hits for a log viewer. The
frontend's job starts where this backend's response ends — deciding chart
type, summarizing, rendering. This backend never does that.

One narrow exception to "read-only": if `ALERT_RULE_CREATION_ENABLED` is
set, the same question can also PROPOSE creating a brand-new Grafana alert
rule — never automatically, always behind a separate explicit confirmation
call. See §11. Off by default; skip §11 entirely if you're not using it yet.

A second, separate opt-in: if `DEPENDENT_QUERY_RESOLUTION_ENABLED` is set, a
compound question where a later part needs the concrete entity resolved by
an earlier part's result (e.g. "which node has the highest CPU utilization,
and how much memory is available on that node?") is resolved in stages
instead of one flat pass. See §14. Off by default, and independent of the
alert-rule flag above — turning one on has no effect on the other.

## 2. Running it / connecting to it

```bash
cp .env.example .env        # fill in a real GEMINI_API_KEY
python run_server.py
```

| What | Where | Notes |
|---|---|---|
| The API itself | `http://localhost:8000` | `API_HOST`/`API_PORT` in `.env` |
| Prometheus | `http://localhost:9090` | `PROMETHEUS_URL` in `.env` — already running per your setup |
| OpenSearch | `http://localhost:9600` | `OPENSEARCH_URL` in `.env` — already running per your setup |
| Interactive API docs | `http://localhost:8000/docs` | Auto-generated by FastAPI, useful for the frontend team to poke at without writing code first |

CORS is wide open (`CORS_ALLOW_ORIGINS=["*"]`) and there's no API key
required by default — correct for local development, both documented in
`.env.example` with a note on what to change before this is ever deployed
anywhere reachable outside your own machine.

## 3. What the frontend sends

`POST /api/v1/query`, JSON body:

```json
{"question": "compare CPU utilization on node-1 and node-2 over the last hour"}
```

```json
{"question": "the available one, not free", "session_id": "a1b2c3d4-..."}
```

| Field | Required | Notes |
|---|---|---|
| `question` | yes | Free-text. Also used as the answer to a clarifying question — see §6. |
| `session_id` | no | Only present when replying to a clarification (§6). Omit for a fresh question. |

That's the entire input contract for `POST /api/v1/query` — one field, one
endpoint, for every kind of question — single-metric, multi-metric,
comparison, follow-up clarification. `POST /api/v1/alerts/confirm` (§11.2)
is a separate endpoint with its own, deliberately narrower, input contract
(`session_id` + optional `confirm`) — it's not reachable through this one.

## 4. What the frontend gets back — the output contract

Every response is:

```json
{"result": { ... }, "session_id": null}
```

`session_id` is non-null **only** when the backend needs a clarifying answer
before it can proceed (§6) — in that case `result` is NOT executed yet (no
data), and the frontend must send the follow-up as a new request carrying
that `session_id`.

`result` always has a `mode` field: `"single"` (one measurement resolved) or
`"multi"` (two or more). This is the one piece of branching logic the
frontend needs:

```js
const entries = result.mode === "multi" ? result.results : [result];
for (const entry of entries) {
  // handle `entry` the same way regardless of which branch it came from —
  // every entry, in both modes, has the exact same set of possible shapes.
}
```

### 4.1 Every shape `entry.status` can be

| `status` | Means | Has `execution`? | Frontend should… |
|---|---|---|---|
| `ok` | Query ran normally. | **Yes** | Render `entry.execution` (§4.2). |
| `panic_mode_best_effort` | Question was underspecified; broadest reasonable interpretation was used. | **Yes** | Same as `ok`, but show `entry.caveat` near the chart — the interpretation was a guess, not a certainty. |
| `ambiguous_metric` | Two+ metrics plausibly match; needs a human pick. | No — never executed | Show `entry.clarification` as a question, `entry.candidates` (`[{name, purpose}]`) as options. Send the user's pick back as a new `question` with the returned `session_id`. |
| `unsupported_metric` | The question wants something this skill package explicitly does not cover (see the matched reference's Do-Not-Use list). | No | Show `entry.explanation`. Nothing to retry — this isn't a "not implemented yet," it's "not applicable." |
| `unmapped` | Nothing in the currently-loaded skill covers this measurement. **This is the status OpenSearch questions get today** — see §7. | No | Show `entry.explanation`. This is expected and will resolve itself once OpenSearch domain coverage ships — no frontend change needed then. |
| `declined` | Nonsensical input, a prompt-injection attempt, or a parameter that needs clarifying (`entry.reason` tells you which). | No | If `reason === "parameter_requires_clarification"`, treat exactly like `ambiguous_metric` (`entry.clarification`, reply with `session_id`). Otherwise just show `entry.explanation`. |
| `out_of_scope_action` | Asked to silence, acknowledge, delete, restart, or otherwise modify something that already exists — this backend never mutates an existing resource, no exception. (Creating a brand-new alert rule is a separate, narrow exception — see the `alert_rule_proposed` row below and §11.) | No | Show `entry.explanation`. Never retryable. |
| `alert_rule_proposed` | **Only when `ALERT_RULE_CREATION_ENABLED=true` (§11).** A brand-new Grafana alert rule was resolved from a verified metric and is ready to create — but hasn't been yet. | No — never executed by `POST /api/v1/query` | Show `entry.alert_rule` (title, condition, threshold, duration) for the user to review, then send `session_id` to `POST /api/v1/alerts/confirm` (§11.2) to actually create it, or to discard it (`"confirm": false`). |
| `validation_failed` | **Not part of the skill's own status vocabulary** — see the callout below. | No | Treat exactly like `declined`: show `entry.explanation`, nothing to retry. |

> **What is `validation_failed`?** Before any query reaches Prometheus/
> OpenSearch, this backend mechanically checks it — is every metric name one
> that's actually documented, is every label key one that was actually
> confirmed to exist right now, does the time range make sense, and so on
> (see §5). If that check ever fails, the frontend gets `validation_failed`
> instead of a made-up chart. **You should never see this in normal use** —
> if you do, it means a bug slipped through, and it's worth telling
> the backend maintainer (it'll also be in the server logs with the exact
> mechanical reason it failed). It behaves identically to `declined` from
> the frontend's point of view: show the explanation, nothing to retry.

`mode: "multi"` responses additionally carry `synthesis`: either `null`
(the ordinary case), or, **only when `DEPENDENT_QUERY_RESOLUTION_ENABLED`
resolved this specific response, §14** — a short, deterministic
natural-language string tying the multiple results together (e.g. "Node-7
is at 92.5% CPU utilization. Available memory on node-7 is 2.00 GB.") —
safe to show as a one-line summary above the individual charts, when
non-null.

### 4.2 The `execution` block — the actual data

Only present on `ok` / `panic_mode_best_effort` entries. Always has these
four fields, then result-shape-specific ones:

```json
{
  "execution_status": "success",
  "result_type": "series",
  "endpoint": "http://localhost:9090/api/v1/query_range",
  "fetched_at": "2026-08-17T10:15:00Z"
}
```

`execution_status` — **check this first, always**:

| Value | Means |
|---|---|
| `success` | Data came back, non-empty. |
| `empty_result` | Query ran fine, backend just has no matching data right now (e.g. asking about a node that isn't currently reporting). Not an error — show "no data for this range," not an error state. |
| `endpoint_error` | Prometheus/OpenSearch was unreachable, timed out, or rejected the query. `error` field has the detail. Show a real error state; safe to let the user retry. |
| `not_executed` | Internal routing problem (shouldn't happen in normal use, same spirit as `validation_failed` above). |

Then, keyed off `result_type`:

**`"series"`** — for line/multi-line charts:
```json
{
  "result_type": "series",
  "series": [
    {
      "labels": {"instance": "node-1:9100", "mode": "idle"},
      "legend_label": "instance=node-1:9100, mode=idle",
      "points": [{"timestamp": "2026-08-17T09:15:00Z", "value": 0.42}]
    }
  ],
  "series_count": 1,
  "had_invalid_samples": false,
  "truncated": false
}
```
`legend_label` is pre-built and safe to render directly on a chart legend —
you never need to reconstruct one from `labels` yourself. `points[].value`
can be `null` (a genuinely missing/unstable sample was hit and safely
dropped rather than sent as invalid JSON) — render it as a gap, not a zero.
When there's more than one series (a comparison question), a `comparison`
key is also present, carrying `{metric_name, series_summaries: [{legend_label,
min, max, avg, latest}]}` — enough to build a "which one is higher"
legend/table without re-deriving it from raw points.

**`"buckets"`** — for bar charts / tables (OpenSearch terms aggregations,
not live yet — see §7):
```json
{"result_type": "buckets", "buckets": [{"key": "node-1", "doc_count": 42}], "bucket_count": 1}
```

**`"hits"`** — for a log viewer / table (OpenSearch plain search, not live
yet — see §7):
```json
{"result_type": "hits", "hits": [{"timestamp": "...", "severity": "ERROR", "body": "...", "resource": {}, "attributes": {}}], "hit_count": 1, "total_hits": 137}
```

Every shape also carries `had_invalid_samples` (bool — some raw samples were
dropped as NaN/Inf/malformed; the rest of the data is still trustworthy) and
`truncated` (bool — the result was capped by a safety limit in `.env`;
`original_count` tells you the true size when this is `true`).

### 4.3 A full worked example

```json
{
  "result": {
    "mode": "single",
    "status": "ok",
    "reference_used": "references/node-exporter/cpu.md",
    "measurement_used": {"type": "raw_metric", "name": "node_load1", "source_metrics": []},
    "data_source": "prometheus",
    "query": "node_load1{instance=\"node-1:9100\"}",
    "time_range": {"from": "now-1h", "to": "now", "step": "60s"},
    "explanation": "1-minute load average for node-1 over the last hour.",
    "execution": {
      "execution_status": "success",
      "result_type": "series",
      "endpoint": "http://localhost:9090/api/v1/query_range",
      "fetched_at": "2026-08-17T10:15:00Z",
      "series": [{
        "labels": {"instance": "node-1:9100"},
        "legend_label": "instance=node-1:9100",
        "points": [{"timestamp": "2026-08-17T09:15:00Z", "value": 0.42}]
      }],
      "series_count": 1,
      "had_invalid_samples": false,
      "truncated": false
    }
  },
  "session_id": null
}
```

## 5. "Validation is deterministic" — what that means and why it matters to you

Every query this backend builds is checked by plain Python (`app/validator.py`)
before it's ever run against Prometheus or OpenSearch — no AI model is asked
to grade another AI model's work, and the same input always produces the
same pass/fail result. It mechanically confirms:
- the metric name used actually exists in the known metric universe (from the
  selected domain references, with catalog status validation available as an
  additive check; never a name the AI invented),
- every label key used in the query was actually confirmed to exist against
  the live Prometheus instance moments earlier (never guessed "by analogy"
  — e.g. it'll block a query that assumes a `node_id` label exists if only
  `instance` was ever actually confirmed),
- the time range and step match the documented grammar and resolve to a
  sane start-before-end range,
- the response shape matches SKILL.md's Output Contract exactly,
- (only for `alert_rule_proposed`, §11) the alert condition actually
  references the resolved metric, and a threshold/comparison/duration/
  folder are all present — never fabricated, and never silently left out.

If any of that fails, the frontend gets a clean `validation_failed` result
(§4.1) instead of a chart built on a query that might be wrong. This is also
why the response is a bit slower than "one AI call" — it's two AI calls
(understand the question, build the query) plus this mechanical check, not
three AI calls like an earlier version of this backend used.

**One nuance worth knowing:** the validator distinguishes *envelope*
problems from *content* problems. If the Generator forgets the top-level
`"mode"` wrapper around an otherwise well-formed result, the pipeline
repairs that automatically before validating (`pipeline._normalize_contract_
shape`) — that's pure structure, not a fabricated fact. If instead a
required *content* field is missing or wrong (e.g. the Router misclassifies
a plain "show me X" request as `out_of_scope_action` and can't supply a real
`requested_action`), the validator correctly refuses to paper over it with
an invented value — you'll see `validation_failed`, and that's the system
working as intended, not a bug to silence.

## 6. The clarification flow (multi-turn)

Some questions are genuinely ambiguous ("show me the available metric" —
available memory? available disk?) or missing something the backend can't
guess (which node?). When that happens:

1. `result.session_id` (top-level, not inside `result`) is non-null, and
   `result` itself has `status: "ambiguous_metric"` or `status: "declined"`
   with `reason: "parameter_requires_clarification"`.
2. Show the user `result.clarification` (a question) and, for
   `ambiguous_metric`, `result.candidates` as pickable options.
3. Send their answer as a normal `POST /api/v1/query`, with `question` set
   to their answer and `session_id` set to the value you got back. The
   backend resolves it using the FULL original question plus their answer —
   don't try to combine them into one string yourself.
4. Sessions expire after `SESSION_TTL_SECONDS` (600s / 10 min by default).
   An expired/unknown `session_id` gets HTTP 410 — treat that as "just ask
   again from scratch."

In `mode: "multi"` responses, if even ONE entry needs clarification, the
**entire** response holds off on execution (all entries), not just that one
— answering the clarification can change how the whole multi-part question
gets resolved, not just patch one piece of it.

**This same session mechanism is also reused for `alert_rule_proposed`**
(§11.2) — but answered by a *different* endpoint
(`POST /api/v1/alerts/confirm`, not `POST /api/v1/query`), since confirming
an alert-rule creation is a fundamentally different action than answering a
clarifying question, even though both hold a session the same way.

## 7. Current OpenSearch status — read this before building any OpenSearch-dependent UI

**Short version: Prometheus questions work end-to-end today. OpenSearch
questions currently come back as `unmapped`, with a clear explanation — not
silently failing, not returning fake data.**

Longer version: the *execution* side for OpenSearch (the HTTP client,
live field discovery, response normalization into series/buckets/hits) is
fully built and unit-tested against realistic mocked responses. What's
missing is the *routing* side — no domain reference file yet tells the
skill "here's what OpenSearch data means and how to query it," because
you're still authoring that content. `skills/references/opensearch-
fundamentals.md` exists (query mechanics only) but is explicitly marked
**infrastructure only, no exporter or domain routes here yet** — see its own
status banner, and `SKILL.md`'s routing table row for it.

Concretely, right now:
- A pure-OpenSearch question ("show me recent error logs for node-1") comes
  back `mode: "single", status: "unmapped"`, with an explanation.
- **A compound question needing both** ("show CPU load and recent error
  logs for node-1") does **not** fail as a whole, and does **not** silently
  drop the logs half. The CPU half resolves and executes completely
  normally; the response becomes `mode: "multi"` with one normal `ok` entry
  for the CPU data and one `unmapped` entry explaining the logs half isn't
  covered yet:

  ```json
  {
    "result": {
      "mode": "multi",
      "results": [
        {"status": "ok", "data_source": "prometheus", "execution": {"execution_status": "success"}},
        {"status": "unmapped", "explanation": "No reference in the currently-loaded skill package covers: recent error logs for node-1. needs an OpenSearch-backed log measurement; no domain reference currently defines one."}
      ],
      "synthesis": null
    },
    "session_id": null
  }
  ```

  Build your frontend's multi-result rendering to expect this shape now — a
  mixed list of resolved and unmapped entries — rather than assuming every
  entry in `results` is always renderable data.

**When your OpenSearch skill content ships** (routing rows + domain files),
nothing in this backend's code needs to change. Add the reference files per
`skills/EXTENDING.md`'s "Adding a New Domain File" / "Adding a New
Datasource" sections, add the routing rows to `SKILL.md` §4, hit
`POST /api/v1/admin/reload-skill` (or restart) — OpenSearch questions start
resolving and executing the same way Prometheus questions do today, no code
change, no frontend contract change. This is the mechanism described in §10.

Use `GET /api/v1/capabilities` any time to see, programmatically, exactly
which topics are currently routed vs. which rows exist but are marked
`"pending"` or carry an infrastructure-only `"note"` — useful for greying
out a UI affordance ahead of time instead of learning it from a failed query.

## 8. Catalog and Markdown responsibilities

**The persistent Catalog (`app/catalog/catalog.json`) is generated from the
vendor metric document, not from Markdown.** This is the final,
implemented architecture as of the vendor-source cutover batches (Batch 1,
Batch 2, the corrective patch, and this finalization batch):

```text
Vendor metric document
        |
        v
app/catalog/vendor_docx.py (parser) -> VendorMetricRecord
        |
        v
app/catalog/vendor.py::build_catalog_from_vendor_records()
        |
        v
app/catalog/catalog.json  (name / type / help / category / exporter,
                            all vendor-sourced; reference_path resolved
                            independently, by metric-name join against
                            existing Markdown -- see below)
```

The production entry point is:

```bash
python -m scripts.generate_production_catalog <vendor_docx_path> [skills_root] [output_path]
```

`app/catalog/generator.py`'s own `generate_catalog()`/`main()` (Markdown-based)
is **not** the production path anymore -- it predates the cutover, and is kept
only for migration/testing/comparison (e.g. diffing a Markdown-derived
candidate against the real, vendor-derived committed catalog; see
`tests/test_vendor_catalog.py`). Its CLI's default output path was deliberately
changed to a non-production filename so running it can never silently
overwrite the real `catalog.json`.

**A new vendor metric does NOT require a Markdown file to enter the
persistent Catalog.** `reference_path` is optional (`None` when no matching
Markdown exists) and every part of the runtime that reads it --
`SkillIndex.metric_directory()`, `app/pipeline.py`'s Level 1 candidate
narrowing, the deterministic validator's known-metric check -- treats a
vendor-only, `reference_path=None` metric as a normal, fully-supported case,
not a degraded one. `skills/scripts/check_metric_directory.py`'s catalog
consistency check does not flag it either.

### Vendor authority vs. Markdown authority (Option C)

```text
CatalogEntry.category   = the vendor document's own Category column, verbatim
Markdown Category bullet = additive retrieval-keyword enrichment only
```

`CatalogEntry.category`, `.type`, `.help`, `.exporter`, and `.name` are all
vendor-sourced and never overridden by Markdown, even when a domain file's
per-metric `Category` bullet is more specific than the vendor's own
(frequently coarser) categorization -- that divergence is expected, not a
bug (`tests/test_vendor_catalog.py`'s divergence check documents this).
What a domain file's `Category` bullet DOES still do:
`app.catalog.generator.build_markdown_category_index()` feeds it into
`app.catalog.rules.generate_keywords()`, applied at request time in
`app/pipeline.py::_get_catalog()`, as additive retrieval vocabulary --
broadening what a question can match against without ever changing what the
Catalog reports as the metric's category. This enrichment is optional (a
metric with no Markdown simply gets none) and never required for Catalog
generation.

`unit` is the one field the vendor document does not reliably provide --
every entry in the real, currently-committed catalog has `unit: None`.
Markdown's per-metric `**Unit:**` bullet remains the sole source of unit
information anywhere in this system; nothing removes or shortens it.

### Why Markdown still matters at runtime -- Level 1 vs. Level 2/3

`SkillIndex.read_reference()` returns a matched domain file's **entire**
Markdown text verbatim into the Generator's prompt whenever the Router
selects that reference. Separately, `app/pipeline.py::_build_metric_metadata()`
(Batch 1/Phase 2) passes a small, structured `{name, type, help, unit}`
block straight from the Catalog for metrics that are CONFIDENT catalog
candidates for the current question ("Level 1"). These are additive, not a
replacement of one by the other:

- **Level 1** (confident catalog match): the Generator gets both the
  structured Catalog block AND (if this reference was also Router-matched)
  the full Markdown text.
- **Level 2** (Router matched a reference, but the catalog wasn't confident
  enough to narrow to a specific metric within it) / **Level 3** (a fresh,
  catalog-unnarrowed routing pass): the Generator's ONLY source of a
  metric's Purpose/Category/Type/Unit and all of its semantic guidance
  (`Use When`, confusable-metric distinctions, query construction guidance,
  guardrails, examples) is the raw Markdown text.

This is why the finalization batch's Markdown-reduction pass (see below)
did not remove any further per-metric basic-metadata bullets
(`Category`/`Purpose`/`Type`/`Unit`) beyond what an earlier phase already
consolidated: `metric_metadata` only ever covers the metrics a specific
question's catalog search confidently narrows to, never every metric under
a Router-matched reference, so Level 2/3 remains a live, load-bearing path
that depends on the Markdown fields staying intact. `Use When`, confusable-
metric distinctions, query construction guidance, guardrails, and examples
are not represented anywhere in the Catalog at all, at any level, and were
never candidates for removal.

The responsibility split is:

| Area | Owns |
|---|---|
| Vendor metric document | Ground truth for name / Prometheus type / What it Measures / Category, for every supported metric |
| Catalog (`app/catalog/catalog.json`) | The metric universe itself: name, type, help, category, exporter, status/reconciliation, retrieval metadata (keywords, priority) -- all vendor-sourced or vendor-derived, plus optional Markdown-category keyword enrichment |
| `skills/SKILL.md` | Shared behavior, routing architecture, common PromQL/query rules, execution/response contract |
| Metric-specific Markdown | Human-authored semantic knowledge: `Use When`, distinctions/confusable metrics, query construction guidance, guardrails, examples, unit (the vendor document doesn't reliably provide one) -- the sole channel for all of this, and the sole channel for ANY of a metric's information when Level 2/3 applies |
| Exporter `overview.md` files | Exporter/domain guidance, entity scope, navigation, shared/domain guardrails, cross-domain semantics -- no Metric Directory table |

Two configuration switches that used to gate catalog integration ("is it
turned on for this deployment yet") -- `CATALOG_ASSISTED_ROUTING_ENABLED` and
`CATALOG_GENERATOR_CANDIDATES_ENABLED` -- were removed once that architecture
was implemented and validated; there is no longer a way to run the normal
query pipeline with catalog integration switched off. A related
validation-only comparison tool, `CATALOG_SHADOW_MODE_ENABLED`, was removed at
the same time. This finalization batch did not reintroduce any feature flag
for the vendor-source cutover either -- catalog generation is unconditionally
vendor-sourced now, with no toggle back to the Markdown-sourced path (that
path exists only as an explicit, separate CLI invocation for
comparison/testing, never as a runtime switch).

One catalog-related switch remains, as a genuine independent capability
rather than a migration switch:

- `CATALOG_METRIC_STATUS_VALIDATION_ENABLED=true` adds catalog metric-status
  validation (rejecting `discovered_pending_review`/`rejected` metrics)
  independently of routing/candidate construction, purely additive to the
  existing known-metric check. Off by default so a deployment whose
  catalog.json currently has many pending-review entries isn't forced to
  start blocking them immediately.
- `CATALOG_RUNTIME_RECONCILIATION_ENABLED=true` (default off) starts a
  background thread (`app/catalog/runtime.py`) that discovers metrics from
  Prometheus at startup and every `CATALOG_RUNTIME_REFRESH_SECONDS`
  (default 300), reconciles them with `catalog.json` and the human decisions
  in `reviews.json`, and publishes the result as the one catalog the pipeline
  reads (`_get_catalog` and `SkillIndex.metric_directory` share it). It also
  switches catalog-status validation on, because the statuses it enforces
  only exist once this is on. Discovery never runs inside a user request; a
  failed discovery, an unreadable `catalog.json`/`reviews.json` or any
  refresh error keeps the last good snapshot. Statuses: a vendor/approved
  metric present at runtime is `approved`, absent is `approved_unavailable`
  (still a valid query metric); a new metric with a Prometheus-reported type
  is `discovered_pending_review` (never usable); an explicitly rejected one is
  `rejected` and stays so across refreshes until `review_catalog clear`.
  Precedence: rejection > vendor entry > approved review record. Review
  decisions are written with `scripts/review_catalog.py` (approval requires
  category, exporter and an existing `reference_path`); `reviews.json` applies
  to the catalog even with reconciliation off (then without availability
  data).
- `ALERT_RULE_CREATION_ENABLED=true` enables optional alert-rule functionality
  only when that workflow is being demonstrated or used. It is unrelated to
  catalog routing.

The catalog does not replace the Router, Generator, Validator, `SKILL.md`, or
ADK session state.

`SkillIndex` retains a compatibility lookup for legacy overview tables where
they still exist. In the current repository, every overview has no table, so
that lookup always reads metric-to-reference mappings from the catalog --
including `reference_path=None` (vendor-only) entries, which it correctly
surfaces into `known_prometheus_metrics` the same as any Markdown-documented
metric.

## 10. How "dynamic" this actually is — adding new coverage later

This was a specific design requirement, so it's worth being precise about
what "automatic" actually covers, post-vendor-cutover.

**Fully automatic, zero code change, ever:**
- A new **label key** appearing on an existing metric in Prometheus (e.g.
  someone adds a `datacenter` label to `node_cpu_seconds_total` tomorrow) —
  `label_discovery.py` queries Prometheus's own metadata live, every
  request. Nothing about label keys is ever hardcoded anywhere in `app/`.

**Requires a Catalog regeneration, but no Markdown and no code change:**
- A new **vendor metric** — add it to the vendor metric document, then run
  `python -m scripts.generate_production_catalog <vendor_docx_path>` to
  regenerate `app/catalog/catalog.json`. The metric is immediately part of
  the persistent Catalog (name/type/help/category/exporter, `status:
  "approved"`) with `reference_path=None`, fully usable by Level 1 catalog
  narrowing, `SkillIndex.metric_directory()`'s catalog fallback, and the
  deterministic validator's known-metric check. No Markdown file is
  required for this.

**Additionally requires a Markdown definition, for semantic depth:**
- Anything beyond bare Catalog membership — `Use When` disambiguation,
  confusable-metric distinctions, query construction guidance, guardrails,
  a verified query example, or Option C retrieval-keyword enrichment from a
  domain-specific `Category` bullet — still requires a
  `### \`metric_name\`` section in the relevant domain file, per
  `skills/EXTENDING.md`. This does not change what the Catalog reports as
  the metric's `category` (see §8's Option C explanation) — only what
  semantic context is available to the Router/Generator when this
  reference is matched, and what keyword tokens Option C contributes.

**Automatic after a restart, or `POST /api/v1/admin/reload-skill`
(no restart needed):**
- A new **domain file** (e.g. `disk-io.md`) with its own metric definitions,
  once it has a routing-table row in `SKILL.md` §4. No Metric Directory row
  anywhere is required — `overview.md` files no longer maintain one.
- A brand-new **exporter** or **datasource**, same mechanism.

Follow `skills/EXTENDING.md` exactly for the authoring steps (it's
maintainer-facing, thorough, and already covers "Adding a Metric," "Adding
a New Domain File," "Adding a New Exporter," and "Adding a New Datasource"
each as a numbered checklist, updated in this finalization batch to
describe the vendor-document-driven flow) — that document, not this one, is
the source of truth for how to author new skill content correctly.

## 11. Alert Rule Creation (SKILL.md §12) — read this before turning it on

**Disabled by default** (`ALERT_RULE_CREATION_ENABLED=false` in
`.env.example`). This optional feature is independent of the normal
catalog-assisted routing configuration. It is the one narrow, explicit exception to this
backend's read-only nature: with the flag on, a question like "alert me if
CPU exceeds 90%" can PROPOSE creating a brand-new Grafana alert rule. It is
never created automatically — a separate, explicit confirmation call is
always required — and it never extends to silencing, deleting, or modifying
an alert that already exists, flag on or off.

### 11.1 Required Grafana-side setup

You need a running Grafana instance with a Prometheus datasource pointing
at the **same** Prometheus this backend already queries via
`PROMETHEUS_URL` — a proposed rule's condition is plain PromQL evaluated by
Grafana against whatever datasource UID you configure, so a mismatch here
doesn't error, it just silently evaluates against the wrong series. Before
setting `ALERT_RULE_CREATION_ENABLED=true`:

1. Create a Grafana **service account** (Administration → Service
   accounts) with at least the **Alert Rule Writer** role, and generate a
   token from it.
2. Note the **folder UID** you want new rules created into (Alerting →
   Alert rules → your folder; the UID is in the URL, not the folder's
   display name).
3. Note the **datasource UID** of the Prometheus datasource pointing at
   your existing Prometheus (Connections → Data sources → your datasource;
   again, the UID is in the URL).
4. Fill in `.env`'s `GRAFANA_URL`, `GRAFANA_SERVICE_ACCOUNT_TOKEN`,
   `GRAFANA_DEFAULT_FOLDER_UID`, and `GRAFANA_DEFAULT_DATASOURCE_UID` — all
   four are required once the flag is on; `app/grafana_client.py` fails
   closed with a clear error rather than guessing if any is missing.
5. Run `python3 scripts/smoke_test_grafana.py` — confirms the token is
   valid and both UIDs actually exist and are visible to it, before you
   try a real question.
6. Set `ALERT_RULE_CREATION_ENABLED=true`.

### 11.2 The propose → confirm flow

This is a **two-step** flow, deliberately — the same shape as the
clarification flow in §6, reusing the exact same session mechanism, but
answered by a different endpoint because confirming is a fundamentally
different action than answering a clarifying question:

1. Ask a normal question through `POST /api/v1/query`:
   `{"question": "alert me if CPU exceeds 90% on node-1 for 5 minutes"}`.
2. If it resolves cleanly, you get back `result.status ===
   "alert_rule_proposed"` (new row in §4.1's table below) with a non-null
   `session_id` — **nothing has been created in Grafana yet.** Show the
   user `result.alert_rule` (title, condition, threshold, duration) and ask
   them to confirm.
3. Send their confirmation to a **different** endpoint,
   `POST /api/v1/alerts/confirm`, with just the `session_id`:
   `{"session_id": "<the id from step 2>"}`. This is the only call in the
   whole flow that actually writes to Grafana. Set `"confirm": false`
   instead to discard the proposal without creating anything.
4. On success: `{"status": "created", "rule_uid": "...", "deeplink":
   "http://.../alerting/grafana/.../view"}` — safe to link the user
   straight to the rule in Grafana. See README.md's API section for the
   full response shape, including every non-success `status` value.
5. Like a clarification session, this is single-use and TTL-bound
   (`SESSION_TTL_SECONDS`, same 600s default) — an expired/already-used
   `session_id` gets HTTP 410 from either endpoint, same as §6.

**Why a plain question can't create a rule in one call:** every alert
rule's condition and threshold has to trace back to something explicitly
verified (SKILL.md §12.4) and the user has to see and explicitly agree to
exactly what will be created — a threshold, folder, or condition is never
guessed on their behalf. If a required piece (threshold value, comparison
direction) is missing from the question, you get `status: "declined"`,
`reason: "parameter_requires_clarification"` instead — handle it exactly
like any other clarification (§6), it just happens to be gathering
information for an eventual alert proposal rather than a chart.

### 11.3 What you will and won't see

Most metrics today don't have a verified alert condition yet — only
`node_cpu_seconds_total` does, as of this version (see
`skills/references/node-exporter/cpu.md`'s Alert query/threshold field).
Asking to create an alert for anything else currently comes back
`status: "unsupported_metric"`, explaining plainly that no verified alert
query is defined for that metric yet — this is expected, not a bug, and
matches the same "never fabricate" discipline every other part of this
skill package already follows for query construction. As more metrics get
a verified Alert query/threshold field (`skills/EXTENDING.md`'s authoring
conventions cover this field the same way they cover Query Examples),
alert-rule creation becomes available for them automatically — no code
change, same mechanism as §8.

**Silencing, deleting, or modifying an existing alert is never in scope,**
flag on or off — a request like "silence this alert" or "delete that alert
rule" always comes back `status: "out_of_scope_action"`, unchanged from
every prior version of this backend.

## 12. New-version replacement policy

You said the plan is: hand this off, keep improving OpenSearch coverage
separately, and later just replace the `backend/` folder wholesale in the
frontend team's copy of the repo. That's exactly how this was built to work:

- **Safe to just swap the whole folder, any time.** The API contract (§3,
  §4) is the stable boundary — a future version can rewrite anything inside
  `app/` or add new domain files under `skills/` without the frontend
  noticing, as long as `POST /api/v1/query`'s request/response shape here
  doesn't change.
- **What WOULD be a breaking change** (none of these have happened in this
  handoff, but flagging so you recognize one if a future version does it):
  a new required top-level field frontend code doesn't handle, a renamed
  `status` value, a renamed `execution_status` value, or a changed meaning
  for an existing field. If a future version ever needs one, it should
  be called out explicitly in that version's own handoff notes, the same
  way this document exists now.
- **Config drift is the actual risk, not code.** Before swapping, diff the
  new `.env.example` against your running `.env` — a future version might
  add a new setting with a sensible default (harmless to miss) or, rarely,
  rename one (would need updating). Everything in `.env.example` has an
  inline comment explaining what it does.
- **This version's specific contract additions**, for the record: the
  `unresolved_topics` → `unmapped`-entries mechanism in §7/§8, the
  `validation_failed` status in §4.1, and (this version) the
  `alert_rule_proposed` status plus the new `POST /api/v1/alerts/confirm`
  endpoint (§11) — disabled by default via `ALERT_RULE_CREATION_ENABLED`,
  so it changes nothing for a deployment that doesn't opt in. All are
  additive — nothing already built against `ok`/`ambiguous_metric`/etc.
  needs to change.

## 14. Dependent Query Resolution (opt-in) — read this before turning it on

Off by default (`DEPENDENT_QUERY_RESOLUTION_ENABLED=false`, `app/config.py`).
Independent of `ALERT_RULE_CREATION_ENABLED` (§11) — either can be on, off,
or both, with no interaction between them (dependency resolution never
considers an alert-rule-creation request at all, regardless of this flag).

### 14.1 What it's for

A compound question where a later part needs the concrete entity resolved
by an earlier part's own result, within the SAME question — e.g. "which
node has the highest CPU utilization, and how much memory is available on
**that node**?" With the flag off, this backend still answers a compound
question like that (§4, `mode: "multi"`), but each part is constructed
independently — the second part has no way to know which specific node the
first part's answer turned out to be about, so it would either need its own
concrete entity from the question itself or come back ambiguous/best-effort
over every instance. With the flag on, a genuine case like this is resolved
in stages instead: the "which node" part runs first, and its real,
already-executed answer (the winning node) is fed into the second part
before its query is even built.

This is unrelated to the existing follow-up/clarification flow (§6) — that
resolves a reference back to a PRIOR turn's question/result; this resolves
a reference within the SAME turn's own compound question.

### 14.2 What changes for the frontend: nothing structural

The output contract (§4) is unchanged. A dependency-resolved response is a
completely ordinary `mode: "multi"` response — same per-entry `status`
shapes (§4.1), same `execution` block shape (§4.2). The only visible
difference is that `synthesis` (§4) may now be a real string instead of
always `null`, for this one kind of response specifically. There is no new
field to branch on, no new status to handle, and no change to how a
clarification (`ambiguous_metric`/`parameter_requires_clarification`) is
handled if one comes back instead — it behaves exactly like §6 already
describes; if a root part of the compound question needs a human answer,
this feature detects that and re-resolves the whole question through the
ordinary flat path instead of executing anything early, so `session_id`
still means exactly what §4/§6 already say it means. (If that flat
re-resolution would itself *execute* — i.e. it answered the dependent part
with no entity filter — it is discarded and the response is a
`validation_failed` result instead; §14.3 item 5.)

### 14.3 What's actually different, mechanically (for you, not the frontend)

With the flag on, the Router may tag each matched reference with an
`intent_id`/`depends_on` pair (SKILL.md §13.2) when the question's own
wording makes one part genuinely conditional on another. This is validated
deterministically (unique ids, no self-reference, no cycle) before it's
ever trusted — anything short of a clean, genuine dependency (including,
overwhelmingly, most requests: no dependency declared at all) is treated
exactly like this flag were off. When a genuine dependency IS found:

1. Every "root" part (no `depends_on`) is resolved and validated in one
   Generator call, then **executed immediately, inside the backend** —
   this is the one real behavior change worth knowing about operationally:
   with this flag on, some responses do a Prometheus/OpenSearch round-trip
   during pipeline resolution itself, before the usual post-pipeline
   execution step, rather than only ever once, always after. Both the root
   call and each dependent call still see the full compound question, so
   each prompt carries a "STAGE SCOPE" block naming the one intent/reference
   that call owns and telling it to leave the rest to the other stage. The
   validator can't enforce that scope itself (its known references/metrics
   are exporter-wide), so the pipeline separately checks, before executing
   the root, that it returned exactly one result per root intent and that
   each result's `reference_used` is the reference that intent was routed
   to.
2. Each dependent part is resolved with its own single Generator call,
   told the resolved entity value from its already-executed parent, and
   MUST retain that value as an explicit filter (SKILL.md §13.4) — a
   generated query that doesn't is never sent to Prometheus/OpenSearch at
   all; it comes back as an ordinary `endpoint_error` (§4.2) instead. The
   entity is taken only from a *successful* parent result with **exactly
   one** series (so the root should be a `topk(1, …)` instant query); a
   parent with zero or several series resolves nothing — the pipeline never
   picks one of several.
3. If a dependent's own generation can't be validated, its contract is
   multi-result or names a reference other than its own, or its parent never
   produced a single resolvable entity (failed, empty, several series), that
   ONE part of the response becomes an ordinary `unsupported_metric` entry
   (§4.1) explaining why — this never fails the whole response. In the
   last case the dependent's Generator isn't called at all.
4. The combined, already-executed response is what the pipeline itself
   returns; the backend's own post-pipeline execution step is skipped for
   this one response (an internal marker the frontend never sees is what
   tells it to skip that step) so nothing is queried against
   Prometheus/OpenSearch twice. `synthesis` names each measurement, e.g.
   "node_cpu_seconds_total for node_id=node-00 is 38.7%. node_memory_
   MemAvailable_bytes for node_id=node-00 is 3.20 GB."
5. **There is no silent flat fallback.** If the *root* stage can't be
   trusted (wrong result count, wrong `reference_used`) the response is a
   single `validation_failed` result (§4.1, treat like `declined`) and
   nothing is executed. Earlier versions re-resolved the whole question
   through the flat path in that case, which has no entity filter and
   produced an every-node memory query with `synthesis: null`.

### 14.4 Testing this

`tests/test_pipeline.py`'s "Dependency-aware compound query resolution"
section (search that heading) covers: the dependency-graph validation
rules on their own (missing/duplicate `intent_id`, self-dependency, an
unknown `depends_on` id, a cycle), that the flag being off ignores any
dependency tagging entirely, a full happy-path staged resolution, the
"generated query dropped the resolved filter" safety check, a parent that
fails to execute, and the "a root needs clarification → abandon staging"
fallback. The "Dependency-aware resolution: stage scope, provenance,
fail-safe" section below it covers the stage-scope prompts, an over-producing
root, malformed root/dependent contracts, failed/empty/multi-series roots,
the guarded pause fallback, and the unchanged ordinary path;
`tests/test_api.py` has one end-to-end run through the HTTP route. The
Router/Generator there are *scripted*, so they prove the pipeline's
deterministic guards and prompt scoping, not that a live model follows
the scoping instruction — that still needs the live check below. There is no separate live-testing tool for this feature the way
§11.1/§13.2 has one for alert-rule creation — the regression-cases file
(`evals/regression-cases.md`, §13.1) is the right place to add a few real
compound questions once you have live Prometheus data with more than one
node/GPU to actually exercise a genuine dependency against.
